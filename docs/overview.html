AWS Reference Sample · Manufacturing AI

Ask your factory anything.

The Agentic Digital Thread (ADT) is a conversational AI engine that connects to your live manufacturing systems — ERP, MES, CMMS, PLM, IoT, and the Unified Namespace (a single live feed of plant-floor data) — and answers cross-system questions in plain language, without months of custom integration.

  • 6+System types queried live — ERP · MES · CMMS · PLM · SiteWise · UNS
  • 0Lines of integration code to onboard a system — the AI maps it
  • 0Production data stored in the knowledge graph — metadata & rules only
Sec. 01 — The Problem

One batch,
four names,
zero answers.

Manufacturers run dozens of systems, each from a different vendor with its own naming and identifiers. The batch your MES calls B-2847 is a different ID in the ERP, another in the maintenance system, and yet another in PLM. Add live OT data — sensors, historians (time-series archives of sensor readings), the Unified Namespace — and no single system can answer a question as simple as “did the machine that made this defective batch have a maintenance issue?”

Sec. 02 — The Value

A generic engine — not a demo, not a point integration

ADT's value is the engine itself: it onboards any manufacturing system dynamically and learns how your systems relate — so cross-system answers stop being integration projects.

VAL / 01

Natural-language answers, live

Ask in plain language. An AI orchestrator plans the question, dispatches per-system agents, and queries your ERP, MES, CMMS, PLM, and OT sources at question time — answers reflect what the systems say right now.

VAL / 02

Onboard any system — no code changes

A four-step AI pipeline — discover → map → resolve → provision — introspects the schema, maps fields to canonical manufacturing concepts, proposes identity rules, and creates the system's query tool; a final verify step confirms the system is answerable. Your systems use the exact same path as everything else.

VAL / 03

A rules engine, never a data store

The Amazon Neptune Analytics knowledge graph holds only metadata: which systems exist, what their fields mean, and how to translate identifiers between them. No production records or sensor readings are stored — only schema metadata and identifier-translation rules.

VAL / 04

Answers get more consistent over time

When the engine discovers a cross-system connection by matching values, it proposes a precise, reusable rule. Confirming it makes the graph smarter for the next question — a human-in-the-loop learning loop, not silent drift.

VAL / 05

Enterprise security, defense-in-depth

WAF and Cognito sign-in enforced at the CloudFront edge (Authorization@Edge), OAuth2 for the agent gateway, Amazon Bedrock Guardrails on the AI, private VPC networking, encrypted data, secrets in AWS Secrets Manager, and least-privilege IAM — layered by design.

VAL / 06

Built on open standards

Agents run on Amazon Bedrock AgentCore and speak the Model Context Protocol (MCP), using the open-source Strands Agents framework. Any external MCP client — for example AWS Quick — can drive the same query gateway; an opt-in bridge gateway lets Quick consume the orchestrator's finished answers.

Sec. 03 — How It Works

From question to cross-system answer

Everything runs inside your AWS account. The web app talks to AI agents through an AgentCore Gateway over MCP; the agents consult the rules engine, then query your systems live.

A note on models: each agent uses a reasoning tier matched to its task — deep reasoning for cross-system planning and synthesis, a fast task tier for narrow, schema-scoped query composition. The defaults are Claude Sonnet 5.5 for the orchestrator and Claude Haiku 5.5 for system agents, defined once in the model catalog (agents/model_catalog.py, single source); both roles switch live from the admin page — no redeploy, no re-onboard — with per-system overrides.

Fig. 02 — What happens when you ask a question

  1. You ask — “Did the machine that produced batch B-2847 have any maintenance issues last month?”

  2. The orchestrator consults the graph for identity and authority rules: which systems know about batches, machines, and work orders — and how their identifiers translate.

  3. Identifiers are translated — the MES batch ID becomes the CMMS asset reference using rules the graph has learned, no guesswork.

  4. System agents query the sources live — each agent runs its query against the actual system (MES, CMMS, sensors) at that moment.

  5. You get one grounded answer — assembled from live results across systems. If the engine found a new connection along the way, it proposes a rule you can confirm.

The graph is a rules engine, not a data store

It holds metadata — which systems exist, what their fields mean, and how to translate identifiers between them — and never stores production data. Even sensor values are read live at query time. Your data stays in your systems.

Sec. 04 — Security & Trust

Layered by design

The reference architecture implements defense-in-depth from the edge to the data layer, under the AWS Shared Responsibility Model. The key layers below ship configured in the sample (the README's security table adds OT network isolation and conversation-memory controls) — and, like the rest of the sample, should be reviewed and adapted before any non-demonstration use.

When conversation memory is enabled, chat turns persist to Amazon Bedrock AgentCore Memory with a 7-day TTL, per-user namespacing, best-effort PII redaction on the stored copy, and removal on teardown.

EdgeAWS WAF

Managed rules (Common, KnownBadInputs, IP reputation) on every CloudFront distribution — the app, and the optional ERP dashboard and HighByte UI.

AuthenticationAmazon Cognito + OAuth2

Browser entry is gated at the CloudFront edge: Cognito Authorization@Edge (Lambda@Edge) redirects unauthenticated users to the Cognito hosted UI, while /api/* keeps its own 401 bearer auth. Machine-to-machine OAuth for the agent gateway. Interactive turns also carry a short-lived app-signed user-identity claim to system agents (optional per-system group enforcement).

AI safetyAmazon Bedrock Guardrails

Prompt-attack detection and content filtering; bring-your-own guardrail via GUARDRAIL_ID.

NetworkPrivate VPC + flow logs

All data and compute in private subnets; VPC flow logs to CloudWatch.

EncryptionIn transit & at rest

HTTPS for all public web traffic through CloudFront; RDS storage encryption; encrypted secrets.

SecretsAWS Secrets Manager

No hardcoded credentials; the demo password is generated or supplied at deploy time.

IAMLeast privilege

Resource-scoped, account/Region-bounded policies; remaining wildcards documented and justified.

MonitoringCloudWatch + Container Insights

ECS Container Insights, flow logs, and structured log groups throughout.

Sec. 05 — Roadmap

Where it's headed

The near-term items below are documented deferred work from the project's own decision records. The second column is directional — a hardening path for teams taking the sample toward real use.

Documented deferred work

Sourced from the repo
  • Response-integrity hardening Answers can already be deterministically audited against captured evidence: the default posture is report-only (shadow capture), annotate is the recommended production posture (grounding score plus a zero-evidence fabrication block), and enforce is retained as an opt-in strict posture. The documented follow-ups harden enforce — elicitation retry, turn-budget tuning — before it could ever become a default. ADR-0046 · ADR-0047
  • Finish the demo/engine separation (CDK phase 2) Remove the last demo-stack parameters from the engine's infrastructure code — completing the "demo data never touches core files" constraint. ADR-0044 · ADR-0030
  • Agent observability drill-down — shipped (opt-in) Per-session tracing (OpenTelemetry spans flowing into CloudWatch Transaction Search) now surfaces in-app on the Agents page, behind an opt-in deploy flag — default off, because continuous trace ingestion has real cost. Remaining follow-up: a one-time confirmation of the span attribute names against a deployed environment with the flag on. docs/agents-fleet-metrics.md
  • Offline graph test double for CI A deterministic in-memory stand-in for the private Neptune graph, so graph behavior can be verified without a deployed environment — it also unblocks mapping-quality evaluation gates. ADR-0024 · ADR-0007 · ADR-0012
  • Row-level provenance & mapping corrections "Show the contributing source rows" behind an answer, and a UI route to correct a mapping directly from the lineage view. ADR-0004 · ADR-0017 · ADR-0003 · ADR-0005
  • Admin-editable configuration Dashboards, cards, and concept layers are declaratively modeled today; exposing them to admins is a designed-but-deferred seam. ADR-0008 · ADR-0018

Future / hardening

Directional
  • Production hardening pass The docs name the concrete items: scope down the deploy role, enable OPC UA message security and authentication, add full NER-based PII scrubbing on memory writes, and review retention and encryption.
  • Multi-tenant & multi-environment support Today's design is single-tenant; shared deployments would need tenant isolation of the graph, secrets, and gateway targets.
  • Enterprise SSO / identity federation An external OIDC identity provider can already be attached to the hosted-UI sign-in (opt-in); replacing demo users with IAM Identity Center or SAML federation remains directional.
  • Broader connector catalog Extend the same dynamic onboarding path (already generic by design) to more industrial sources — SQL Server, SAP OData, historians, direct OPC UA.
  • CI/CD & drift management Pipeline-ized deploys gated by the offline graph double, with declarative data-mode configuration.

Directional items are informed by the sample's own "not production-hardened" guidance; they are possibilities, not documented commitments.
