# Post-deploy steps

On a fresh deployment the HighByte MCP bearer token and AWS IoT SiteWise
publishing are configured **automatically** (the setup AWS Lambda function
creates and stores the MCP token; the bundled project ships with the SiteWise trigger
enabled). The one step every deployment needs is **onboarding** systems; which
systems depends on how you deployed.
Terminology follows [`glossary.md`](glossary.md).

Checklist:

1. [Onboard systems](#1-onboard-systems): **required for all deployments**; what you onboard depends on the deployment mode.
2. [Retrieve sign-in credentials](#2-retrieve-sign-in-credentials)—as needed.
3. *(HighByte only)* [Upload a HighByte license](#3-upload-a-highbyte-license)—recommended; without one, HighByte runs in a short (~2-hour) trial, after which **all data features stop** (no telemetry from OPC UA to AWS IoT SiteWise, no MCP data).
4. *(HighByte only—fallback)* [Recreate the MCP bearer token](#4-configure-the-highbyte-mcp-bearer-token) and [re-enable SiteWise publishing](#5-enable-highbyte-aws-iot-sitewise-publishing)—both are automatic on a fresh deploy; the manual steps are only needed if you must recreate them.

> **Important:** The HighByte Amazon CloudFront URL changes whenever the
> HighByte stack is recreated. The `/adt/highbyte-url` SSM parameter is refreshed
> automatically by `deploy.sh`; if you deploy the stack directly, run
> `highbyte/post_deploy.sh` (or update that parameter) and restart the ADT app
> task so it picks up the new URL.

## 1. Onboard systems

> **Important:** The orchestrator can't query any data until systems are
> onboarded. Until then the chat responds with "no systems connected".

Onboarding connects the agents to your systems and builds the knowledge graph.
What the catalog holds after a deploy, and so what you onboard, depends on the
deployment mode:

| Deployment | The catalog after a fresh deploy | What you onboard |
|---|---|---|
| **Base** (`deploy.sh` with no data flag, the default) | Empty: no system is registered. | Your own systems. Choose **Connect New System** and follow [Connecting your own data sources](deployment.md#connecting-your-own-data-sources). |
| **Seed or simulator** (`--seed`, `--simulator`) | The six bundled demo systems below, plus the Indianapolis plant's **Indianapolis MES** and **Indianapolis Plant Maintenance**, all registered, none onboarded. | The six bundled systems. The two Indianapolis systems are optional; onboard them to add the fourth site. |

### To onboard the bundled systems

1. Open the ADT app and sign in as `ADT`.
2. Choose **Architecture** in the top navigation.
3. Choose the **Onboard** tab. Each available system has an **Onboard** button.

On a seed or simulator deployment, onboard the six bundled systems:

| System | Description |
|--------|-------------|
| **ERP** | Orders, inventory, suppliers, customers (all sites). |
| **Milwaukee MES** | Manufacturing execution—Milwaukee bottling plant. |
| **Detroit MES** | Manufacturing execution—Detroit automotive plant. |
| **Cedar Rapids MES** | Manufacturing execution—Cedar Rapids food plant. |
| **CMMS** | Work orders, schedules, assets (all sites). |
| **PLM** | BOMs, engineering changes, specifications (all sites). |

Each system's status changes from **Available** to **Onboarded** when its
onboarding finishes. The first onboarding of a system also creates its agent
runtime, so it takes longer than a later one.

Onboard these optional systems when their prerequisites are deployed:

| System | Prerequisite |
|--------|--------------|
| **HighByte Intelligence Hub** | MCP bearer token configured (see [Configure the HighByte MCP bearer token](#4-configure-the-highbyte-mcp-bearer-token)). |
| **AWS IoT SiteWise (Direct)** | AWS IoT SiteWise asset hierarchy created by the HighByte pipeline (see [Enable HighByte AWS IoT SiteWise publishing](#5-enable-highbyte-aws-iot-sitewise-publishing)). |
| **AWS IoT SiteWise (i3X)** | A reachable i3X server. Onboard from the UI through **Connect New System → AWS IoT SiteWise (i3X)** with the server's endpoint URL and bearer token (stored in AWS Secrets Manager). `SITEWISE_I3X_URL` is only needed for the demo quick-link (see [`highbyte.md`](highbyte.md)). |

### Verify onboarding

Go to the **Dashboard** tab—the system chips show all onboarded systems. Ask
a question, for example *"What is the current OEE for Milwaukee?"*

## 2. Retrieve sign-in credentials

All demo credentials derive from one secret. The password is generated by
AWS CloudFormation **once at the first deploy**, stored in the `adt-demo-password`
AWS Secrets Manager secret, and is **stable across subsequent deploys**. A
`-c demo_password=...` override exists for
throwaway deployments only—it embeds the value in the synthesized template
(see the caveat in the README's Security section). Retrieve the current value:

```bash
aws secretsmanager get-secret-value --secret-id adt-demo-password \
  --query SecretString --output text --profile <YOUR_PROFILE> --region <YOUR_REGION>
```

| Application | URL source | Username |
|-------------|-----------|----------|
| **ADT app** (main dashboard) | `ADTComputeStack` output `ADTCloudFrontUrl` or configured `ADTCustomDomainUrl` | `ADT` |
| **ERP dashboard** (Streamlit) | `ADTERPDashboardStack` CloudFront output or `https://erp.<custom-domain>` | `erp` |
| **HighByte UI** | `ADTHighByteOpcuaStack` output `HighByteDistributionURL` or `HighByteCustomDomainUrl` (`https://highbyte.<custom-domain>`) | `ADT` (edge sign-in), then `administrator` |

When a custom ADT domain is configured, CDK owns the enabled human-facing
names: the configured ADT name itself plus `erp.<custom-domain>` under
`--simulator` and `highbyte.<custom-domain>` under `--highbyte`. Certificates,
DNS aliases, and Amazon Cognito callback/logout URLs are automatic.

All three browser surfaces authenticate through Amazon Cognito user pools. ADT
Authorization@Edge is on by default, so unauthenticated browser navigation goes
to the Cognito hosted UI; `/api/*` bypasses the edge redirect and retains the
application's own session/bearer authentication and 401 responses. The
HighByte UI then uses its built-in `administrator` account for the HighByte
sign-in itself.

Get the ADT app URL:

```bash
aws cloudformation describe-stacks --stack-name ADTComputeStack \
  --query "Stacks[0].Outputs[?OutputKey=='ADTCloudFrontUrl'].OutputValue" \
  --output text --profile <YOUR_PROFILE> --region <YOUR_REGION>
```

> **Note:** The HighByte admin password is the same value (propagated to the
> HighByte secret). The HighByte stack exposes only the **ARN** of that secret as the
> `HighBytePasswordSecretArn` output—never the plaintext password.

The video-briefing feature on the dashboard is auto-configured (Amazon Bedrock
generates the script, Amazon Polly synthesizes narration, `ffmpeg` composes the
MP4, and Amazon S3 stores the result with a 7-day expiry). No setup is needed;
`ffmpeg` is installed in the app image.

## 3. Upload a HighByte license

HighByte runs **unlicensed in a short (~2-hour) trial**. When the trial
expires, the hub turns off its data features: telemetry stops flowing from OPC UA
to AWS IoT SiteWise and the MCP/namespace tools return no data. The deployment
health-checks the port that a trial expiry closes, so Amazon Elastic Container
Service (Amazon ECS) replaces the hub task, and the new task starts a fresh trial.
That typically takes about four minutes, and data stops for that long. If the hub
is still down after that, sign in to it and choose **Reset Trial** in its license
banner. For uninterrupted or sustained use, upload a license:

1. Open the HighByte UI and sign in as `administrator`.
2. Go to **Settings → License → Choose File → Import License**.

The license file is **not** bundled in this repository—obtain it from HighByte
([highbyte.com](https://highbyte.com)).

## 4. Configure the HighByte MCP bearer token

> **Note:** Automatic. On a fresh deploy the setup Lambda function creates an MCP API key in
> HighByte and stores it in the `adt/conn/highbyte` secret (JSON
> `{"token": ...}`), which the ADT app reads. No action needed unless you must
> recreate it.

**Manual fallback (only if auto-creation did not run or you rotated the key):**

HighByte limits API-key names to **8 characters, alphanumeric or underscore
only**. Use a name such as `mcpkey`, not `mcp-bearer-token`.

1. Get the HighByte URL:
   ```bash
   aws cloudformation describe-stacks --stack-name ADTHighByteOpcuaStack \
     --query "Stacks[0].Outputs[?OutputKey=='HighByteEndpoint'].OutputValue" \
     --output text --profile <YOUR_PROFILE> --region <YOUR_REGION>
   ```
2. Open the HighByte UI and sign in as `administrator` (password: see
   [Retrieve sign-in credentials](#2-retrieve-sign-in-credentials)).
3. Go to **Settings → Users → administrator → API Keys → Create API Key**.
   Copy the generated value (shown once; format `mcpkey.<base64>`).
4. Store it for the ADT app. **Preferred:** paste it into the ADT admin page
   (**Admin → HighByte token**), which writes the canonical
   `adt/conn/highbyte` secret (JSON `{"token": ...}`) and wires the
   System node for you. To do it by CLI instead (note the JSON shape the app
   parses):
   ```bash
   aws secretsmanager put-secret-value \
     --secret-id adt/conn/highbyte \
     --secret-string '{"token":"<YOUR_MCP_API_KEY>"}' --profile <YOUR_PROFILE> --region <YOUR_REGION>
   ```
   Then restart the ADT app task so it picks up the token.

**Verify MCP** (optional): `Settings → MCP` shows **Enabled** (default); the
endpoint returns `401` without a token and `200` with it.

For the deep reference (ports, MCP testing, the Unified Namespace), see
[`highbyte.md`](highbyte.md).

## 5. Enable HighByte AWS IoT SiteWise publishing

The bundled project ships with the `NameSpace_to_SiteWise` pipeline's trigger
**enabled**, so telemetry flows automatically once HighByte starts. AWS IoT
SiteWise asset models are pre-created by `highbyte/DeploySitewiseModels.py`
(run automatically by `deploy.sh`).

What happens automatically:

- On the first few cycles a transient `Building Assets` status appears as
  HighByte creates roughly 170 assets (Enterprise → Sites → Areas → Lines →
  Processes). It clears on its own.
- After two or three cycles, telemetry appears in the AWS IoT SiteWise console.

Do **not** "reset the SiteWise connection cache"—HighByte v4.4 has no such UI
button, and deleting the connection breaks the pipeline (`SIteWise does not
exist`—the capitalization is verbatim: the bundled HighByte connection is
named `SIteWise` in `intelligencehub-configuration.json`). It is unnecessary on
a fresh deploy.

If you want to verify models *before* data flows, set the
`NameSpace_to_SiteWise` trigger `config.enabled` to `false` in
`config/highbyte/intelligencehub-configuration.json`, then enable it in the UI
(**Pipelines → NameSpace_to_SiteWise → Triggers**) when ready.

If models are missing, (re)create them (idempotent):
```bash
python3 highbyte/DeploySitewiseModels.py --profile <YOUR_PROFILE> --region <YOUR_REGION>
```

See [`highbyte.md`](highbyte.md) for the model/asset hierarchy and
troubleshooting.
