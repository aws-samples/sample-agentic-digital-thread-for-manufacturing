Any system.
Any schema.
Any identifier format.

The ADT engine contains no assumptions about your systems — not the vendor, not the schema, not how identifiers are shaped, not whether the source is a relational database or an OT time-series feed. Everything system-specific is discovered at onboarding, stored as metadata, and refined by feedback — never hard-coded. That is why the same engine serves bottling, machining, food, or chemicals without custom integration code.

Sec. 01 — The Problem

Same physical thing, four names

Every manufacturing system names the world its own way. A production run, a work order, a machine — each carries a different identifier in every system that touches it. The bundled sample landscape shows the shape of the problem:

MES · Bottling WO-YYYYMMDD-XXXXX date-encoded work orders
MES · Machining DET-RUN-0001 site-prefixed sequences
CMMS KF2000-MKE-01 MODEL-SITE-SEQ serials
Other systems 7f3a…-uuid opaque UUIDs
"The same physical thing carries a different identifier in each system — that is exactly the gap the digital thread closes." docs/architecture.md · data model

The classic answer is a point integration per system pair — each one a project, each one maintained by hand, each one hard-wired to one vendor's schema. ADT's answer is a generic engine: cross-system answers stop being integration projects.

Sec. 02 — The Mechanism

Four pillars of adaptability

Adaptability is not a claim — it is an architecture. Four design decisions, each with its own decision record, keep every system-specific fact out of the code and in the data.

Pillar / 01

AI-driven onboarding discovers any schema

One registration path for every system: discover → map → resolve → provision. The pipeline introspects whatever schema it finds, maps fields to canonical manufacturing concepts, resolves identity keys, and creates a dynamic query tool per system. Entity resolution is layered — a deterministic path first, then a precedent-based heuristic, then a constrained LLM classification that can even mint a new entity concept for a genuinely novel table. Every table resolves to exactly one entity, so any system can join the thread. Connections, too, are owned by onboarding: the record it writes is the single source of truth, resolved dynamically at connect-time — no redeploy to point at a new system.

ADR-0040 (dynamic entity + identity for ANY system) · ADR-0031 (onboarding-driven connections) · docs/architecture.md (provision creates the dynamic tool)
Pillar / 02

The graph holds rules, never data

The Amazon Neptune Analytics knowledge graph is a rules engine in a semantic-layer position: it stores which systems exist, what their fields mean, and how to translate identifiers between them — concepts, field mappings, identity rules. Metadata only. No production rows, no sensor readings, no credential values. Because the engine consults these rules at question time instead of baking them in, no assumption about a source's format ever hardens into code — swap the source, re-onboard, and the rules change while the engine does not.

docs/architecture.md (rules-engine concept) · ADR-0057 (semantic-layer positioning: "rules engine" = what's inside; "semantic layer" = where it sits)
Pillar / 03

Crosswalks are learned, humans confirm

How one system's identifiers map to another's is mined from the data itself — same-row identifier sets and intra-system joins are captured at onboarding, and repeated per-value matches observed during real questions are promoted into a single general rule when enough independent confirmations accumulate (a count, deliberately not LLM confidence). Every learned mapping enters one proposal lifecycle — pending → accepted / rejected / superseded — and auto-accept stays off by default: a human steward confirms before a proposal becomes applied truth in the graph. User feedback and corrections flow through the very same lifecycle.

ADR-0003 (unified proposal lifecycle) · ADR-0041 (onboarding-time capture) · ADR-0043 (per-value → rule promotion; auto-accept OFF)
Pillar / 04

Domain context is data, not code

What a "batch" means in your plant, which lifecycle states are bookkeeping, which system is authoritative for each shared concept, what the data does not cover — a standard ten-question intake captures it, and each answer lands on an engine surface: business context, field annotations, identifier-semantics patterns, per-concept authority rules, coverage statements. Vocabulary and semantics live in the graph as steward-supplied data, so the same engine serves bottling, machining, food, or chemicals — the domain is loaded, not programmed.

Sec. 03 — Any Format

Identifier styles the engine never assumes

Four identifier conventions from the bundled sample landscape — structured, sequenced, model-encoded, opaque. None of them appears in engine code. Each is discovered at onboarding and related to the others through identity rules in the graph.

WO-YYYYMMDD-XXXXX Bottling MES date-encoded work order
DET-RUN-0001 Machining MES site-prefixed run sequence
KF2000-MKE-01 CMMS asset serial MODEL-SITE-SEQ convention
7f3a41e2-… Opaque UUID no embedded meaning at all
Resolved through identity rules, never guessed. A confirmed crosswalk — for example, a CMMS serial to another system's opaque UUID — is a precise, reusable rule in the graph. Name-similarity guessing produces wrong joins; a stored rule produces the same join every time. cmms assets.serial_number "KF2000-MKE-01" ⇄ uuid "7f3a…"  ·  value_mapping → identity rule (steward-accepted)

Sec. 04 — What Stays Honest

Adaptable, not credulous

A learning engine is only trustworthy if its knowledge is inspectable and its boundaries are declared. Three guarantees hold no matter what systems are connected:

  • No production data in the graph The graph stores how to reach systems and how to translate between them — never production rows, never sensor readings, never credential values (secrets live in AWS Secrets Manager; the graph carries only the ARN). "Rules engine, not a data store" is the governance claim, and it is deliberately load-bearing.
  • Absence honesty — "no coverage" beats an invented number Declared coverage boundaries are part of the domain context. Where the data does not cover — a site without OT telemetry, an all-NULL inspection column — the engine says so instead of fabricating a plausible figure. Absence is where fabrication lives; declaring it is the honest answer that builds trust.
  • Every learned rule is reviewable, with provenance All learned mappings pass through one proposal lifecycle with a full audit trail: who or what proposed it, from which evidence, and when it was accepted, rejected, or superseded. Auto-accept is off by default — applied truth in the graph is steward-confirmed truth.
